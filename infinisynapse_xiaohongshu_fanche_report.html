Part A ・ 已确认需求维度（来自上一轮讨论，原样保留）

1介绍
用户输入小红书笔记链接或正文文本 → 系统检测是否夸大宣传、绝对化用语、疑似软广/营销话术，输出「可信度评分 + 避坑要点清单 + 改写建议」。本质是给单篇笔记做一次「可信度体检」。
2出发点
小红书种草内容泛滥，用户「踩雷」成本高（买到不好用的、被夸大效果坑）。平台自身不提供可信度判断；年轻人对「反种草 / 避坑」有强情绪共鸣，且乐于分享「翻车」经历。
3切口
不做「全网舆情监控」，只做单篇笔记的可信度体检——范围小到一周末可做。聚焦一句话：「这篇到底值不值得信？」
4创新点
反向视角：别人做「帮你种草 / 找好物」，你做「帮你排雷」。把 InfiniSynapse 的语义分析能力用在「内容可信度判别」这个新维度上，而非商品比价。
5差异化
基于此前作品长廊扫描（我推断是）：现有偏购物决策类（省钱比价 / 商品侦探 / 财格），无人做「内容可信度体检」。差异 = 评估对象从「商品」变成「话术 / 内容」。
6预期效果
极易传播（「来测测你收藏的笔记翻没翻车」有社交裂变潜力）；真人试用门槛极低（贴链接/文本即出结果）；最有利于拉高占 60% 分的真实调用。
7使用技术
前端：输入框 + 链接/文本解析；后端：调 InfiniSynapse 做语义风险分类（绝对化词、功效夸张、软广信号）；渲染：评分条 + 清单卡片。数据以用户自贴文本为主，预置几篇公开笔记做 demo。
8InfiniSynapse 实现
把笔记文本作为分析输入，用多轮 task 让模型按你定义的「翻车维度」打分并给理由；可选建 RAG 知识库装入「广告法禁用词 / 绝对化用语清单」提升一致性。 我推断是：REST 走分析任务接口（如 POST /v1/query 类，具体路径以官方 API 文档为准）；本地开发可用 agent_infini task new/ask 联调。
9还需操作
① 你拍板「翻车」评分维度与权重，避免模型随意判；② 准备 demo 数据集（几篇典型翻车 / 正常笔记）；③ 小红书反爬 / 登录墙→ 前端以「粘贴正文」为主入口（已更正 不能只靠直采链接、直采失败降级 —— 更正：直采在浏览器端会撞 CORS+反爬，直接不做链接抓取，只做粘贴，见 B5/E1）。
10制作路径
D1 前端 + API 打通（最小可用：粘贴文本→评分）；D2 维度细化 + 清单渲染 + 示例数据；D3 打磨 UI + 邀请真实用户试 + 提交。
11潜在风险
误判引发争议（把真实分享判成软广）；绝对化词库不全；链接直采失败需降级为粘贴；「可信度」界定主观，专家评审可能觉得维度不够严谨。

B3 ・ 竞品与现有方案基准（市场差异） 新增

现有方案它做什么我们的差异
小红书官方「避雷」/「踩坑」话题UGC 标签聚合，无自动判断我们给单篇自动化可信度评分，不是靠人肉刷帖
广告法禁用词检测工具（各类在线 checker）只查"违禁词"，不判内容可信度我们做语义级（功效夸张、证据缺失、利益相关未披露），不止字面词
第三方"成分/功效"查询（如美丽修行）查商品成分，不查"话术"评估对象是内容话术而非商品本身
本次比赛现有作品（比价/侦探/财格）帮"买得值"我们帮"信得过的才买"，反向视角

结论：直接竞品弱、间接竞品不重叠，蓝海切口成立（我推断是，基于公开工具与长廊扫描）。

B4 ・「翻车」评分维度体系（可操作化定义） 新增

原需求第 9 项要求"你拍板维度与权重"。下面给出建议的 6 维度框架，供你确认/调整。每个维度都可被 InfiniSynapse 任务判定并给证据句。

维度判定信号（可检测）建议权重示例证据
① 绝对化用语"最/第一/100%/绝无/永久"等20%"全网最好用"
② 功效夸张违背常识的速效承诺20%"3 天瘦 10 斤"
③ 软广/营销话术引流话术、品牌暗广、利益诱导20%"姐妹冲这个链接"
④ 证据缺失结论无图/无数据/无来源15%"亲测有效"无图
⑤ 利益相关未披露恰饭未声明、伪装素人15%通篇好评无瑕疵
⑥ 情绪裹挟制造焦虑/紧迫感促单10%"不买就后悔"
总分公式（建议）：可信度 = 100 − Σ(维度命中严重度 × 权重)。输出 0–100 分 + 每维度命中证据句。维度与权重可在配置里调整，避免模型随意判。

待其他专家确认：① 维度是否增减？② 权重是否合理？③ 严重度如何分级（轻/中/重）？这部分直接决定专家评审眼里的"严谨度"。

B5 ・ 信息架构与交互设计建议 新增

前端结构
单页三区：输入区（文本框 + "粘贴笔记"按钮 + 可选链接框）→ 结果区（总分卡 + 维度条 + 证据清单 + 改写建议）→ 行动区（分享卡片 / 测下一篇 / 看示例）。
结果呈现
用维度条而非单一分数降低焦虑；每条命中配"原文高亮 + 为什么算翻车"；结尾给"可改进版话术"而非判死刑。
输入方式 已更正
链接直采失败（反爬）→ 自动提示"请粘贴正文" —— 更正（前端工程师 E1）：浏览器端直采会撞 CORS + 反爬，不应做链接抓取尝试，直接只做"粘贴正文"输入框，体验更稳。原"可选链接框"建议砍掉，避免用户以为能用、实际失败。
首屏拉新
放 2–3 个预置 demo 笔记（一篇翻车/一篇正常），用户点一下即出结果，零门槛体验。

B6 ・ 可用性与无障碍（Accessibility / 包容性） 新增

✅ 必须做：① 评分用文字+图标双标识，不只靠颜色（色盲友好）；② 移动端字号≥16px、点击区≥44px；③ 结果区支持屏幕阅读器（语义化标签 + aria-live 播报分析完成）；④ 粘贴框支持键盘全操作。
⚠️ 易忽略：① 分享卡片若含大段彩色高亮，打印/灰度下信息丢失；② 老年用户不懂"软广"术语，需白话解释；③ 弱网环境下骨架屏要有离线提示。
💡 机会：把"无障碍自检"本身作为卖点（"连色盲都能看懂的避坑报告"）。
🚫 风险：纯颜色评分若被专家用无障碍插件检测扣分，影响 40% 评审里的"完整性"。

B7 ・ 隐私、合规与伦理 新增

议题风险缓解
用户粘贴文本归属笔记内容含他人原创，你存储/分析是否合规默认不持久化用户文本，仅用于本次分析；明确告知
小红书反爬/ToS直采链接可能违反平台条款前端以"粘贴正文"为主，链接直采仅作便利、失败即降级
"软广"标签名誉风险把真实分享误标软广，可能侵害博主名誉结果措辞用"疑似/建议复核"，加"仅供参考，非官方认定"免责
广告法边界我们判定"违禁词"若出错，用户据此改稿仍可能违规提示"以平台/法律最终认定为准"，不替代法律意见

待其他专家确认：是否在隐私政策里声明数据处理方式？比赛作品通常需一个简单说明页，建议 D3 加一个"关于/隐私"弹层。

B8 ・ 成功度量指标 新增

比赛层（命门）：真实用户数、活跃 API 调用量（占 60%）。设计上从 D1 就埋：分享按钮、demo 一键测、社媒传播钩子。已更正 这些埋点能"证明真实调用" —— 更正：用户指标 60% 以 InfiniSynapse 平台后台数据为准，自己埋点不算数。埋点的真实作用只是产品内部复盘，不能替代平台后台统计（见 Part X #1、官方确证 C2）。
产品层（给专家看"完整度"）：① 任务完成率（粘贴→出报告）；② 平均分析耗时（目标 ≤3s）；③ 分享率（测完导出卡片占比）；④ NPS / 满意度（提交后轻量问卷）。
埋点建议（内部复盘用，非评分依据）：事件 = 粘贴成功 / 报告生成 / 分享点击 / 复测。用于对内优化体验，不用于向平台证明调用量。

B9 ・ InfiniSynapse 实现深化（多轮任务 + RAG + 提示框架） 新增

调用骨架：前端 → 你的后端（持有 API Key）→ InfiniSynapse 分析任务。

多轮任务设计（建议）：
① task new "对这篇小红书笔记做可信度体检：{正文}"
② task ask {id} "按 6 维度逐条判定，给证据句和严重度"
③ task ask {id} "输出 0–100 可信度分与改写建议"

RAG 知识库（提升一致性）：建一个知识库装入《广告法绝对化用语清单》《常见软广话术样本》，让每次判定标准统一、可解释。

我推断是：REST 具体端点/字段以官方 API 文档为准（分析任务类接口，如 /v1/query 或 agent_infini 对应的 HTTP 形态）；本地用 agent_infini task new/ask 联调最稳。Key 通过 init --api-key 配置，切勿硬编码在前端。

E4 ・ 法务/合规 · 署名意见（承接产品 E3）

⚖️ 法务/合规顾问（Legal & Compliance）

核心判断：项目有三类风险，均可通过措辞与声明规避，不构成"不能做"，但必须做。
① 名誉/误判风险：将真实用户笔记判为"软广/翻车"若出错，可能侵害博主权益。强制措辞：结果页用"疑似营销话术""可信度待你判断"，加"本结果由 AI 生成、仅供参考、非官方认定"免责条。绝不输出定性结论（如"这是软广"）。
② 平台关系：声明"与小红书官方无关，仅基于用户主动提交的文本做语义分析，不抓取平台数据"。避免被解读为对小红书的负面评判工具。
③ 数据合规：用户粘贴文本默认不持久化（Part B7），隐私弹层写明"文本仅用于本次分析"。若后期存日志用于优化，需单独征得同意。
④ 广告法边界：我们判定"违禁词"若出错，用户据此改稿仍可能违规——声明"不替代法律/平台最终认定"。
"能做的边界很清晰：只做'疑似'提示 + 免责，不做'定性'判定。做到这点，风险可控。"
传递回发起人（行业场景研究员）：合规要求已明确，请在最终可行性结论中确认：D3 必须含隐私/免责弹层 + 结果页免责条，否则不应提交。

E5 ・ 发起人汇总（行业场景研究员）

✅ 专家共识：① 切口稀缺、传播力强，是 4 候选最优；② 技术栈轻，前端 1 天 + 后端转发 0.5 天可出 MVP；③ 用自建 RAG 知识库作 data_source 解决"无用户库"问题；④ 合规边界清晰（只做"疑似"+免责）。

Part F ・ InfiniSynapse 做啥 vs WorkBuddy 做啥（角色边界讲解）

本章专门回答一个容易混淆的问题：这个比赛里，InfiniSynapse（参赛平台） 和 WorkBuddy（你现在用的 AI 助手 / 开发环境） 分别扮演什么角色？基于此前比赛介绍与官方规则，把边界讲清楚。

F1 ・ 两个角色的本质区别

维度InfiniSynapse（参赛平台）WorkBuddy（AI 助手 / 你的开发环境）
它是什么 比赛主办方提供的数据分析 PaaS。提供 Server API、AI 分析能力、数据源/RAG 管理、用户账号体系与评分后台。 你日常使用的通用 AI 助手 + 代码/文档工作台。能读文件、写代码、检索、生成报告、发邮件——但不是比赛平台，不参与评分。
在比赛里的角色 被集成方 + 裁判。你的作品必须调用它的 API 做分析；它的后台统计"注册用户数 + 活跃调用量"直接决定你 60% 的分数。 你的生产力工具。帮助你读官方文档、设计维度、写前端/后端代码、生成这份报告、发邮件——这些都不计入比赛评分。
谁产生"真实调用" 只有它。用户通过你的应用发起的分析请求，打到 InfiniSynapse 的 /v1/query，才算"活跃使用量"。 WorkBuddy 调用 InfiniSynapse（比如我帮你联调测试）产生的请求，算你自己的调试调用，不算真实用户拉新。
一句话区分：InfiniSynapse 是"你的作品要调用且据此打分的那套云端服务"；WorkBuddy 是"帮你把作品做出来的那把瑞士军刀"。前者进比赛、后者不进。

F2 ・ 具体到"种草翻车检测"，各自负责什么

🟦 InfiniSynapse 负责（平台侧）

① 跑分析：接收笔记文本 + 你的知识库(data_source)，用 LLM 按 6 维度判定、出可信度分与证据句。

② 存知识库/RAG：你建的"广告法禁用词 + 软广话术样本"知识库，作为 data_source 被查询引用。

③ 账号与计分：用户通过「InfiniSynapse 登录」注册/授权；后台统计活跃量，决定 60% 评分。

④ 发 API Key / clientId：你申请 Key 调 /v1/query，申请 SSO 凭证接登录。

🟩 WorkBuddy 负责（你的工具侧）

① 写代码：生成前端页面、Serverless 转发函数、SSO 回调处理。

② 读官方文档 / 检索：用 anysearch 拉比赛公告、API Reference、SSO Guide（本报告的 Part D 来源）。

③ 设计：和你一起定 6 维度权重、用户画像、交互方案（本报告 Part A/B）。

④ 文档与协作：生成这份评审报告、汇总专家意见、发邮件给你和其他专家。

⑤ 联调辅助：帮你跑 curl 测 /v1/query、验证返回结构（但这是你自己的调试调用，不计入评分）。

F3 ・ 一个必须划清的红线（避免白忙）

WorkBuddy 帮你做的"调用 InfiniSynapse"不算比赛成绩。 比如我（WorkBuddy）在联调时用自己的 Key 调了 100 次 /v1/query，这 100 次只算你的调试流量，不会变成"真实用户活跃量"。真正计分的是：真实用户通过你部署的公网应用 → 触发 InfiniSynapse 分析。所以 WorkBuddy 的价值在于"把作品做出来并做对"，而不是"替你刷调用"。
对应到排期：WorkBuddy 在 D1–D3 帮你产出代码、文档、联调脚本；但最终 60% 分数要靠你把应用部署上线 + 真实用户通过它调用 InfiniSynapse +（最好）接 SSO 拉新来拿。WorkBuddy 不能替代这一步。
