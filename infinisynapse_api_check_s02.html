二、两套接口并存 —— 这是关键事实

此前的报告 Part C 把「API 端点歧义」表述为"二选一的路径不一致"，不准确。实际是两套独立并存的接口，适用场景不同：

维度① 简化同步接口 推荐本项目用② 完整异步接口（Server API Reference）
地址POST https://api.infinisynapse.cn/v1/queryGET /api/ai/events（SSE 订阅）
+ POST /api/ai/message（发消息）
是否官方是，但仅出现在大赛快速集成示例，不在 Server API Reference 正文是，Server API Reference 主推
调用模式同步，一次请求一次返回 JSON异步：先建 SSE 长连接，再 POST 发消息，结果经 SSE 推送
请求体{query, data_source}WebviewMessage：{type:"newTask",text,connId} 或 {type:"askResponse",taskId,askResponse:"messageResponse",text}
data_source 字段有（直接挂数据源/RAG ID）无——需先在平台用 POST /api/ai_rag_sdk/enabled 启用 RAG，再发消息
适用单篇笔记一次性体检，最简单多轮对话、需持续交互的复杂分析

三、/v1/query 请求体与返回结构（官方示例原文）

请求（官方大赛公告原文）

import requests
response = requests.post(
    "https://api.infinisynapse.cn/v1/query",
    headers={"Authorization": "Bearer sk-xxxx"},
    json={
        "query": "分析最近一周的销售数据，找出下滑最明显的品类",
        "data_source": "your_datasource_id"
    }
)
print(response.json())

确认字段：

  • query（string，必填）：自然语言问题 / 分析指令
  • data_source（string，必填）：已启用的数据源或 RAG 知识库 ID（即我们自建的"翻车评分知识库"）
  • 鉴权：Authorization: Bearer <API Key>（Key 仅放服务端，绝不进前端）
  • 域名：注意是 api.infinisynapse.cn（非 app.infinisynapse.cn），走 HTTPS

返回结构（官方示例只写 print(response.json())，未展开字段）

⚠️ 待实测确认：官方快速示例未给出 /v1/query 的具体响应 JSON 字段（不像 Reference 的 {code,message,data} 统一信封那样明确）。因此 S1.4 联调时必须用真实 Key 跑一次，把响应结构（是否含 code/data、分析正文在哪一层）完整记录下来，再写前端解析。这是 D1 不可跳过的验证项。

四、对执行计划的直接影响（需同步更正）

结论：本项目走 ① /v1/query 同步接口最合适——单篇笔记一次 POST 拿结果，且原生支持 data_source 挂我们自建的"翻车评分知识库"，比 ② SSE 那套少写一整套连接管理代码，2 天内更稳。

  • S1.2 转发函数：改为转发到 https://api.infinisynapse.cn/v1/query，body 为 {query: 拼接后的分析指令, data_source: 自建知识库ID}。无需实现 SSE 订阅。
  • S1.1 建知识库：在 InfiniSynapse 建 RAG 知识库拿到 ID，作为 data_source 传入（与 Reference 里"先 enable RAG 再发消息"等效，但 /v1/query 把这一步内联进请求体）。
  • S1.4 联调：除验证返回结构外，额外确认 /v1/query 单次耗时（目标 ≤ 数秒，前端需加载态/流式降级）。
  • S2.5/2.6 SSO：与接口选择无关，仍按原计划作为 D2 后段可选项。
